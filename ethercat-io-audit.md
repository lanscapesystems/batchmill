# Batchmill EtherCAT I/O audit

Reviewed the `production` branch at [`8b4a3b20eb7f`](https://github.com/lanscapesystems/batchmill/commit/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e). Scope covers IgH process data, the C daemon, command and state exchange, rack commissioning, and the TypeScript mill scan. This is a static source audit. The standalone NX-ECC203 bench run demonstrated digital I/O and a complete working counter with the OD5256 and ID5442. It did not exercise the Batchmill daemon or establish production timing, recovery, or analog and scale behavior.

**Disposition.** Keep the separate C I/O task and TypeScript supervisory logic. Fix the command watchdog, per-cycle bus validity, and startup and recovery behavior before using this daemon to command production equipment. Resolve rack mapping and rotation detection before commissioning the affected channels.

## Findings

### P0 · The command watchdog expires with a healthy controller and can leave the output image stuck at zero

The backend writes only when the serialized output values change. The daemon treats a changed file modification time as the heartbeat and clears outputs after two seconds without one. A steady run command therefore expires while the backend is healthy, and the backend's cached string prevents republishing the same image. The daemon uses second-resolution `st_mtime`, so it can also miss newer commands within the same second, including a stop. It refreshes the timeout before confirming a readable, valid command image. Each output is applied independently as lines are parsed, allowing the cyclic task to transmit a mixture of two command images. [Backend writer](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/src/ioDaemon.ts#L45) · [Daemon reader](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/ethercat-rt/io_daemon.c#L284)

**Fix.** Publish a complete, sequenced command image on a recurring heartbeat even when values are unchanged. Include controller session, configuration generation, enable state, and sequence. Validate the complete image before refreshing its deadline. Hand it to the cyclic task as one coherent image. Enforce freshness with monotonic elapsed time inside the cyclic task. Derive the timeout from the measured update interval and required process response. Reject older or incompatible images and acknowledge the applied sequence in status.

### P0 · Invalid process data can still drive logic and outputs

The cyclic task calls receive and domain process, then reads every mapped input and writes every output. Link and WKC are logged approximately once per second. There is no per-cycle quality gate on complete WKC, expected slaves, slave OP state, or error status. Meanwhile the writer keeps publishing on its own schedule, and the backend treats a recent file as fresh. A live writer can therefore conceal stale or invalid field data. The rack watchdog runs on a three-second timer and checks presence and entry counts. It cannot provide cycle-level data quality. Missing state also leaves ordinary backend inputs at their last value. [Cyclic task](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/ethercat-rt/io_daemon.c#L431) · [State freshness](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/src/ioDaemon.ts#L28) · [Backend input handling](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/src/mill.ts#L810) · [Rack watchdog](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/src/mill.ts#L137)

**Fix.** Publish a single input image per valid cycle with sequence, acquisition timestamp, validity and a fault reason. Require the expected topology, required slaves in OP, and complete process-data WKC before accepting inputs or enabling outputs. Inhibit the affected equipment when required data is invalid. Treat last-good values as diagnostic display data. Configure and physically verify how each output module and drive responds when the cable is removed or the host stops sending, because the host cannot deliver its safe image over a failed link.

### P0 · Startup and fault recovery have no explicit output arming handshake

The startup path activates the master and the command reader accepts the existing file if present. It has no session check, startup enable handshake, or acknowledgement that the controller and daemon agree on the same rack configuration. The orderly shutdown path sends zero values in a final cycle. That path cannot cover power loss, a killed process, or an unreachable slave. The all-zero policy also assumes raw zero is suitable for every DO and AO. [Command intake and zeroing](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/ethercat-rt/io_daemon.c#L276) · [Startup and shutdown](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/ethercat-rt/io_daemon.c#L485) · [Service restart policy](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/ethercat-rt/feedmill-io-daemon.service#L6)

**Fix.** Start inhibited, require verified topology and stable valid cycles, then accept a fresh command from the current controller session and explicitly arm. On communication or heartbeat fault, return to an inhibited state. Require the mill sequence to re-establish permissives and authorize a new start before reenabling motion. Define and verify per-output behavior against the actuator, drive, and field wiring. Keep personnel safety functions in the designated safety system.

### P1 · Rack verification can accept the wrong card or bind the wrong physical point

Discovery keeps only entries in the `0x6xxx` and `0x7xxx` ranges. The backend assigns them to declared cards by running position in each direction list, using entry counts for verification. It does not establish slot identity, direction, width, or bit layout for each binding. It can report cards as `ok` when the EtherCAT tool is unavailable. The daemon also discards the starting bit returned by IgH and reads analog values as fixed-width words without checking the mapped field width. Omron describes PDO grouping and alignment, so a list sorted by physical slot is insufficient for mixed cards. [Discovery and allocation](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/src/ethercat.ts#L77) · [Offline fallback](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/src/ethercat.ts#L141) · [PDO registration](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/ethercat-rt/io_daemon.c#L367) · [Omron W519, Appendix A-4](https://www.omron-ap.com/data_pdf/mnu/w519-e1-18_nx-ecc20_.pdf)

**Fix.** Commission an explicit manifest with expected coupler identity, detected NX slot IDs from `0xF050`, and the approved PDO location, direction, offset, width and type per signal. Verify it against live discovery on activation and following a rescan or replacement. Fail closed on missing, duplicate, misaligned, oversized or unverified mappings. Keep simulated and live verification states distinct. Stage a new configuration, inhibit outputs, and show activation success only after the daemon acknowledges the new generation in valid OP. The current restart path swallows failures and will skip retry if the generated file already matches. [Configuration deployment](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/src/ethercat.ts#L306)

### P1 · The RPM calculation can fault a healthy auger

The daemon already samples and counts rising edges from ordinary digital inputs. The mill calculates RPM from count changes over a nominal 100 ms supervisory scan. At 500 RPM with one target, edges arrive every 120 ms. Even with perfect capture, the 100 ms window can alternate between zero and one pulse, producing approximately 0 or 600 RPM. After the grace period, one low window is enough to trip. The backend ignores the published edge timestamp and skips rotation enforcement if the counter is missing. A daemon restart can also reset the count while the backend retains the old baseline. [Edge capture](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/ethercat-rt/io_daemon.c#L452) · [Rotation logic](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/src/mill.ts#L866)

**Fix.** Keep the 16-point NX-ID5442 for the proposed 15 shafts and qualify pulse capture on the installed hardware. Have the C task publish the latest valid edge interval and edge age, with the input cycle and daemon generation. Seed the edge state from the first valid input after start or recovery. Derive RPM from valid edge intervals, use a separate no-edge timeout for a stopped shaft, and treat unavailable feedback as a distinct condition. Apply startup grace, low-speed qualification and hysteresis against monotonic elapsed time. With the ¾-inch target traveling at a 2-inch radius, nominal pass time at 500 RPM is about 7.2 ms. Verify the actual minimum sensor ON time against the longest valid sample gap at maximum speed and worst installed air gap.

### P1 · A 4 ms setting does not establish a 4 ms timing guarantee

The daemon uses a monotonic absolute schedule and attempts memory locking and FIFO priority. It continues if either fails, measures no deadline misses, and can run catch-up iterations after delays. It creates file worker threads after elevating the main thread, with default attributes that ordinarily inherit scheduling settings. Logging is performed in the cyclic task, and the backend calls synchronous EtherCAT CLI commands and service restarts from the same Node process that runs the mill timer. That can stretch supervisory scans and delay commands. [Daemon scheduling](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/ethercat-rt/io_daemon.c#L511) · [Cyclic logging](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/ethercat-rt/io_daemon.c#L435) · [Synchronous CLI wrapper](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/src/ethercat.ts#L19) · [Mill timers](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/src/mill.ts#L123)

**Fix.** Give only the cyclic task the intended real-time policy. Keep file I/O, diagnostics, and service management outside it, and off the supervisory control event loop where they can block it. Count missed deadlines and record maximum valid input sample gaps and execution time. On overrun, resume at a future deadline and invalidate any data whose acquisition continuity matters. Make degraded scheduling visible and qualify the exact Debian host and NIC under load.

### P1 · Analog and RS1201 support needs typed, model-specific commissioning

The backend assumes a common raw analog full scale of 27648 and labels it a placeholder. C reads AI as signed 16-bit, scale as signed 32-bit, and AO writes a signed 16-bit cast. The RS1201 mapper assumes the first allocated entry is weight. These assumptions cannot establish engineering scaling, channel diagnostic quality, correct failure output, or a workable scale calibration handshake. [Analog conversion](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/src/ioDaemon.ts#L8) · [Raw I/O handling](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/ethercat-rt/io_daemon.c#L466) · [Scale mapping](https://github.com/lanscapesystems/batchmill/blob/8b4a3b20eb7f06f045a6e8ac62ec34f68337011e/feedmill-backend/src/ethercat.ts#L253) · [Omron W565, sections 6 and 7](https://assets.omron.eu/downloads/latest/manual/en/w565_nx-series_load_cell_input_unit_users_manual_en.pdf)

**Fix.** Enable production AI/AO only for identified card models with validated ranges, encoding, engineering conversion, limits and failure response. For each RS1201, verify the actual PDO map, weight and status encoding, validity, stability, and zero/span behavior with the installed load cell. A Sysmac-free calibration workflow requires confirming the command and response PDOs and implementing the documented handshake, then verifying calibration after a power cycle.

## PLC-style target behavior

Use a scan with a clear order: **receive and qualify field data → latch one input image → evaluate control and permissives → select one complete output image → send and report status**. The C task owns EtherCAT exchange and the output permissive. The supervisory task owns sequencing, recipes, and the slower equipment logic. Exchange coherent images with explicit quality and acknowledgement. Any interlock that needs a response inside the supervisory scan budget belongs in a task with a verified response time. Establish the maximum allowed detection and reaction times before selecting watchdog and alarm delays.

## Implementation and acceptance order

1. **Command and bus integrity.** Hold an unchanged run request for longer than the old watchdog timeout, issue a stop in the same second as a start, reject malformed or partial commands, kill each process separately, and unplug the EtherCAT link. Confirm bounded output response and prove outputs stay inhibited across recovery until reauthorized.
2. **Rack identity and addressing.** Exercise wrong-card, wrong-slot, missing-card, duplicate mapping and failed activation cases. On the bench, check each physical point against the HMI point and verify the active configuration generation. Include a mixed digital and analog rack.
3. **Rotation and timing.** Drive all 15 inputs from known pulse sources at representative speeds, including measured worst-case pulse width at 500 RPM. Compare counts with a reference under production host load. Verify maximum sample gap, no false low-speed trips at normal speed, and bounded trips at low speed and when pulses stop.
4. **Analog and weighing.** Measure analog input and output at known electrical test points and verify behavior when signal or EtherCAT is lost. Verify RS1201 weight and calibration with known weights, induced invalid/stale data, and a restart. Release these functions only once the physical results match the commissioned profiles.

## Status of the analog / RS1201 finding (P1)

Done in code, checked offline (`ethercat.check.ts`), not on hardware:
- Production AI/AO/scale only for the models in the verified table (W522, W565); anything else is left out of `io.conf` with a warning.
- RS1201 weight and status are taken from the unit's own PDO block (0x6000/0x6001/0x6002 at the per-unit shift), checked for 16/16/32-bit widths; Detection Status bits 0-3 invalidate the reading. Calibration runs over the documented SDO handshake.
- Analog points must map to 16-bit PDO entries, or they are left out.
- Read Rack now reads the unit settings (W519 A-7-10, index 0x5000 + (unit-1) x 0x20): channel enable (AI 0x5002, AO 0x5010) must be TRUE, and the AO load-rejection hold setting (0x5012) must be 4 = Zero Count, so a lost host or bus drops the output to 0 V / 4 mA. A point failing either is excluded from `io.conf` with the reason; unreadable settings only warn.
- The input/output ranges of the xx03 / xx603 models are fixed by the model (W522 range tables), so they cannot differ from the catalog's full scale.

Still to do on the bench: confirm the 0x5xxx SDO reads work through the coupler (and the BOOL read as uint8), measure AI/AO at known test points and on signal loss, check the AO output when EtherCAT is unplugged, and verify RS1201 zero/span with known weights and after a power cycle.
