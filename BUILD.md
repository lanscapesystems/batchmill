# Build and Run

## Prerequisites

- Node.js 22+ (feedmill-backend's better-sqlite3 version requires it)
- npm

## Project structure

```
feedmill-backend/    TypeScript control service (Express + WebSocket + SQLite)
hmi-prototype/       Next.js browser HMI
```

## Install dependencies

```bash
cd feedmill-backend && npm install
cd ../hmi-prototype && npm install
```

## Build

```bash
# Backend — compiles TypeScript to dist/
cd feedmill-backend
npm run build

# Frontend — produces .next/ production bundle
cd ../hmi-prototype
npm run build
```

## Type-check only (no emit)

```bash
cd feedmill-backend && npx tsc --noEmit
cd ../hmi-prototype && npx tsc --noEmit
```

## Run (development)

Start both in separate terminals:

```bash
# Terminal 1 — backend (auto-reloads on save)
cd feedmill-backend
npm run dev
```

```bash
# Terminal 2 — frontend
cd hmi-prototype
npm run dev
```

- Backend: `http://localhost:3001`
- Frontend: `http://localhost:3000`
- HMI WebSocket: `ws://localhost:3001/ws/hmi`
- REST API: `http://localhost:3001/api/v1/state`

The backend has no simulated-I/O mode — it only reads/writes real points through `ethercat-rt/io_daemon.c` (see below). Running it without that daemon and a real EtherCAT rack means inputs/outputs just stay at their last known values.

## Run (production)

On the real Debian target, use `feedmill-backend/install/install.sh [ethercat-nic]` (leave the NIC off to pick it from a list) — it is the one-shot production installer: builds the IgH EtherCAT Master and `io-daemon`, deploys and builds the backend natively (required — `better-sqlite3` is a native addon, so a `node_modules` copied from another OS/arch won't load), and installs/enables the systemd units (`ethercat.service`, `feedmill-io-daemon.service`, `feedmill-backend.service`, `feedmill-hmi.service`). Each run builds a new read-only release under `/opt/feedmill/releases/`, switches the `current` symlink, health-checks it, and reverts automatically on failure; `sudo feedmill-rollback` flips back to the previous release by hand (code only, not `mill.db`). Running the backend manually without the daemon/rack is still possible for frontend-only work:

```bash
cd feedmill-backend && npm start        # node dist/server.js
cd ../hmi-prototype && npm start        # next start
```

## Environment variables

| Variable | Default | Description |
|---|---|---|
| `PORT` | `3001` | Backend HTTP/WebSocket listen port |
| `MILL_DATA_DIR` | `feedmill-backend/data/` | Directory for `config.json` and `mill.db` |

## Data files

All persistent state lives under `MILL_DATA_DIR`:

| File | Format | Contents |
|---|---|---|
| `config.json` | JSON | Equipment, connections, bins, ingredients, recipes, scales, Omron rack, global config. Written atomically (tmp + rename). Editable — no versioning. |
| `mill.db` | SQLite WAL | Active batch state, batch history, inventory events, fault log. `synchronous=FULL` for power-loss safety. |

On first run with no `config.json`, the backend writes default configuration from `loadDefaults()`. On subsequent starts it loads from the file.

Outside `MILL_DATA_DIR`, the backend and `io-daemon` hand off real I/O through three more files, all written atomically (tmp + rename): `/etc/feedmill/io.conf` (generated by `syncIoConf()` from the rack + I/O mapping — never hand-edited), `/run/feedmill/io-state.json` (daemon → backend, every 20ms), and `/run/feedmill/io-command.txt` (backend → daemon, every scan). If the backend stops updating the command file for 2 seconds, the daemon forces every output to 0 rather than latching the last value.

## Configuration edit guards

Equipment and I/O config commands (`AddEquipment`, `RemoveEquipment`, `UpdateEquipment`, `AddConnection`, `RemoveConnection`, `ConfigureScale`, `RemoveScale`, `ConfigureOmron`) require:

- No active batch, or batch is PAUSED
- No motors currently running

Bin, ingredient, recipe, and global config edits have no guard.

## Batch recovery

If the backend starts and finds an incomplete batch in `mill.db`, it restores the batch in PAUSED state with a `W-BA-REC` warning fault. The operator reviews the scale reading and chooses to resume or abort.

During dosing, batch state is persisted to SQLite at every state transition and every 5 seconds while feeding. Up to 5 seconds of weight data may be lost on a hard power cut.

## Frontend ↔ Backend connection

The HMI connects to the backend WebSocket at `ws://localhost:3001/ws/hmi` by default. Override with the `?backend=` query parameter:

```
http://localhost:3000?backend=ws://192.168.1.100:3001/ws/hmi
```

When disconnected, the frontend falls back to local-only state (edits stay in the browser store until the backend reconnects).
