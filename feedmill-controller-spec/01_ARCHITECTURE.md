# 01 — Software and Hardware Architecture

## Function

Deliver a configurable feed mill control system in which the Debian control service owns all ordinary machine operations, the web app handles user interaction and business workflows, and Omron/serial adapters expose hardware.

## Current production architecture

The split C++ Control Service / Hardware Service design below, and EtherNet/IP as the fieldbus, are a **deferred future architecture** — not what is built. The current, only-supported production path is a single Node.js/TypeScript process (`feedmill-backend`): Express REST API + one WebSocket endpoint (`/ws/hmi`) + SQLite (`better-sqlite3`, WAL journal mode, `synchronous=FULL`) for persistence, all in one event loop with a 100ms control scan. It reaches the EtherCAT bus two ways: the IgH EtherCAT Master's `ethercat` CLI (wrapped in `src/ethercat.ts`) for rack discovery/verification, and a separate realtime C program (`ethercat-rt/io_daemon.c`, run as `feedmill-io-daemon.service`) that does the actual cyclic PDO exchange for every digital/analog I/O point, edge-counts rotation sensors, and reads NX-RS1201 load-cell weight — the Node process's 100ms scan can't touch the EtherCAT process image directly or sample fast pulses itself. Node and the daemon hand off through two files under `/run/feedmill/` (`io-state.json`, `io-command.txt`); the daemon's own config at `/etc/feedmill/io.conf` is generated by `syncIoConf()` in `src/ethercat.ts`, never hand-edited. There is no simulated-I/O mode in this process — it only reads/writes real I/O through the daemon. Deployment is one script, `feedmill-backend/install/install.sh`, run once on the Debian target.

## Proposed future logical components (EtherNet/IP, split services)

```text
Browser / HMI (React + TypeScript)
       | HTTPS REST commands, WebSocket state/events
API / Web Service (auth, validation, recipes, reports)
       | versioned local IPC, no direct output writes
Control Service (C++: scheduler, batch engine, equipment,
                 route manager, alarms, inventory event requests)
       | fresh commands / telemetry / fault state
Hardware Service (EIP scanner, serial scale adapters, I/O images,
                  control-engine heartbeat supervision)
       |                 |
Omron NX-EIC202      Serial scale indicators
```

**Process split is PROPOSED**: C++ control service and independently monitored I/O service; API implementation may be C++ or Python. Prefer a single well-defined typed IPC protocol over ad hoc shared variables. Control must not block on DB, HTTP, logs or frontend.

## Timing

- **REQUIRED:** target under 30 ms from *physical input transition* to *physical output transition* for designated non-safety I/O paths.
- **PROPOSED:** PREEMPT_RT kernel, 5–10 ms deterministic control cycle, separate NIC dedicated to the I/O network (EtherNet/IP scanner or EtherCAT master, per [03 Equipment and I/O](03_EQUIPMENT_AND_IO.md)), preallocated memory/no blocking I/O on critical thread, tagged monotonic timestamps, bounded command queues.
- RPI and timeout settings depend on actual coupler, NX unit configuration and driver capabilities. Preliminary values are not verified guarantees.
- End-to-end budget includes sensor filtering, NX input update, cyclic network timing, controller queue/scheduling, output update, and module actuation.
- Scale latency and process fill cutoff are separate measurements; serial indicator updates may be slower than the main I/O loop.

## Deployment

- Fanless industrial PC powered from cabinet 24 VDC (model TBD); automatic on with power available (BIOS/AT setting **must be verified**).
- Debian minimal, no desktop required, watchdog driver verified with the actual board, read-only root when commissioned, writable transaction data partition, controlled update path.
- `systemd` units with explicit dependencies; API service failure must not halt an otherwise healthy running batch by default.
- Browser may run on a panel, tablet or network PC. Loss of browser must not directly alter output state.

## Security

- Restrict control LAN; use authentication/authorization for every command; API validates equipment ownership and current operational state.
- Keep EIP network separate from general LAN when feasible; no direct Internet exposure for control services.
- Versioned configuration updates, operator/audit trails, backups, restore procedures, controlled deployment and service restart.

## Design criteria

- No fixed I/O channel assumptions in equipment logic.
- No fixed topology assumptions in batch logic.
- Simulated adapters must implement the same interfaces as physical adapters.
- Document safety, fault, and power-loss behavior for every device class.
